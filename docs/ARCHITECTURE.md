# 架构与不变量

## 问题边界

输入是单个会话、按原始顺序排列的 ITCH 5.0 消息；离线文件使用两字节大端长度 + 消息本体。首版使用 `std::istream`，没有网络接收、MoldUDP64/SoupBinTCP 重组、缺包恢复、跨通道排序或 `mmap`。未验证文件来源和会话完整性时，输出只表示输入片段的状态，不代表交易所真实全量簿。

流水线：`Reader → Decode → Apply → per-symbol Book → BBO/校验输出`。Reader 校验前缀和完整消息，Decode 校验确切长度、类型及字段；Apply 在更改状态之前校验 ID、symbol/locate、数量和价格。失败时命令行返回非零，不输出看似成功的最终行情。暂不支持的消息明确失败，不能静默跳过会影响订单簿的事件。

## 数据模型

- `order_ref → {locate, symbol, side, remaining, price}` 为活跃订单索引；另保存当日已见 ID 集合。order_ref 按规范当日唯一，删除后复用仍是错误。M1 为正确性保留这份额外索引，性能阶段再评估空间成本。
- 每个 symbol 有买、卖两棵按整数价格排序的价位树，节点保存该价位**可展示剩余股数**。买方取最大价，卖方取最小价。M1 不保存队列优先级，因为输出仅为价位聚合与 BBO。
- `locate → symbol` 从 A 消息建立临时映射，后续同一 locate 不能指向另一 symbol。完整版本将由 Stock Directory (R) 建立正式映射，并校验 A/F 中的 symbol。
- 价格为 `uint32` Price(4)，例如 `1000000` 表示 `100.0000`；不使用浮点存储。数量聚合使用 `uint64`，每次加法检查溢出。
- 单线程按输入顺序重放。所有数据结构都拥有自己的数据，消息缓冲区可以复用；没有 `reinterpret_cast`、未对齐整数读取或固定容量写入。

## 失败语义和终态目标

截断、长度不匹配、非法 side/数量、重复 ID、未知 ID、locate 不匹配均为硬失败。M1 的 Add 和 Delete 在应用前完成业务校验。后续支持 E/C/X/U 时，需要进一步保证复合更新的原子性，尤其 Replace 不能删除旧单后才发现新 ID 冲突。

完整 ITCH 数据还含系统、股票、成交、交叉盘等消息。有些不改变可展示簿，但必须按规范分类处理并统计；不能简单把未知类型忽略。未来如接入网络，应先验证顺序与缺包检测，再消费消息。下一阶段先完善离线正确性，然后设计快路径，避免优化改变语义。

## 扩展设计

M2 添加 R/F/E/C/X/D/U 生命周期、类型表和不可影响簿的消息分类；保留简单 `std::map` 参考实现。M3 用相同事件流分别驱动参考实现与候选实现，逐条比较订单数、每 symbol 的各价位数量和 BBO。M4 才考虑按 symbol 分片、稠密价格窗口、预分配、`mmap` 输入；价格越界或容量耗尽必须有正确回退或明确失败。任何优化必须在相同语义下被测量。
